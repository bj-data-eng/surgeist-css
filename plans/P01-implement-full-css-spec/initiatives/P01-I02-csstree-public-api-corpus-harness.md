# P01-I02 CSSTree Public API Corpus Harness Specification

## 1 Outcome

`surgeist-css` shall own a committed, license-complete CSSTree parser corpus and
an in-process Rust integration-test harness that executes every imported case
through the crate's intentional public parsing and application-strict validation
front doors. The corpus shall supplement focused model and grammar tests with a
broad independent acceptance, rejection, recovery, and panic-freedom oracle.

The harness shall use neutral expectation artifacts generated by
`surgeist-generator`; it shall not execute CSSTree, JavaScript, Node.js, a
browser, a network client, or a generator during ordinary Cargo tests. A single
corpus load shall serve the complete integration-test binary, and cases shall be
partitioned into a small stable set of context-family tests so normal crate
verification remains fast and failures identify every affected upstream case.

The initiative starts from CSSTree commit
`88e3d965c0b1628642a30a841745b410d6835052`, package version `3.2.1`, whose
`fixtures/ast` Git tree is
`bfadc7a7a8d93dce59a27fa7df3bb0f6f6a623d8`. That tree contains 74 regular JSON
files and 935 cases: 721 upstream-parsed cases and 214 upstream-rejected cases.
Every imported case shall execute and shall be classified exactly once.

This initiative depends on the completed public parsing and diagnostic contract
of `P01/I01`. It does not redefine that contract. Any corpus case that exposes a
defect in a feature claimed complete by `P01/I01` remains failing evidence until
the owning parser behavior is corrected; the harness shall not weaken the oracle
or label an implementation defect unsupported merely to become green.

## 2 Ownership And Non-Goals

`surgeist-css` owns:

- the committed CSS test corpus, its upstream attribution, and its compatible
  source and expectation pins;
- one CSS-owned per-case oracle that assigns the public probe and exact expected
  Surgeist outcome for every generated case ID;
- the integration-test-only consumer model for the neutral expectation schema;
- context adaptation from upstream parser fragments to complete CSS inputs;
- the mapping from upstream expectations to Surgeist public parsing,
  diagnostics, and application-strict validation outcomes;
- deterministic corpus completeness, classification, and failure reporting;
- focused verification and maintenance documentation for the adopted corpus.

`surgeist-generator` owns source-checkout verification, fixture decoding,
neutral expectation generation, report generation, corpus checking, atomic
publication, and generator-side recovery. The CSS harness shall consume its
committed artifacts and shall not copy those operations into this repository.

The following are outside this initiative:

- executing or embedding CSSTree, Node.js, npm, a browser, or JavaScript;
- comparing CSSTree AST objects to Surgeist authored syntax types;
- adding a CSS serializer or comparing `canonical_css` to Surgeist output;
- changing production CSS syntax, parser, diagnostic, or validation APIs solely
  to make corpus tests convenient;
- reaching into `src/parser`, `src/validation`, private syntax constructors, or
  other crate internals from the corpus harness;
- treating generic CSSTree value parsing as proof of property-specific CSS
  validity;
- cascade, selector matching, resource loading, variable substitution, layout,
  rendering, or other non-parser behavior;
- a normal or development dependency from production `surgeist-css` code to
  `surgeist-generator`;
- automatic source acquisition, background corpus updates, CI network access,
  or unreviewed movement to a newer CSSTree revision;
- replacing the crate's focused grammar, modeling, recovery, diagnostic,
  property-specific, or public-API tests.

The ignored checkout at `tmp/csstree` is research and maintenance input only. It
is not a committed corpus artifact, build input, or ordinary test prerequisite.

## 3 Evidence And Dependencies

### 3.1 Pinned Upstream Corpus

The pinned upstream checkout is the canonical Git repository
`https://github.com/csstree/csstree.git` at
`88e3d965c0b1628642a30a841745b410d6835052`. Its package metadata identifies
`css-tree` version `3.2.1` and the MIT license. The upstream license names
Roman Dvornov and requires preservation of the copyright and permission notice
in substantial copies.

No pinned case is marked skipped upstream. Twenty-one parsed cases live in files

treated as synonymous with a clean Surgeist parse.

Thirty-four cases carry upstream parser options. The observed option keys are
`atrule`, `parseAtrulePrelude`, `parseCustomProperty`, `parseRulePrelude`,
`parseValue`, and `property`. Unsupported or semantically irrelevant option
combinations require an explicit CSS-oracle outcome; the harness shall never
silently ignore an option while claiming the case active.

### 3.2 Upstream Case Semantics

The upstream fixture loader accepts either one case object or an array of case
objects under any top-level label. It classifies an individual case as rejected
when that case contains an `error` member; the top-level label itself does not
determine outcome. Array members receive distinct identities derived from the
group label and member position.

The pinned tree contains 60 top-level array groups with 297 members. Of those,
24 are non-`error` groups with 108 members. A neutral importer that accepts arrays
only under a literal `error` key would lose or reject valid upstream structure.

Upstream rejected cases normally force CSSTree's parse-error callback to throw.
The neutral corpus needs only the raw input and parsed-versus-rejected outcome;
upstream diagnostic prose, JavaScript error classes, AST objects, and source
locator implementation are not Surgeist contracts.

### 3.3 Generator Compatibility Prerequisite

The observed `surgeist-generator` candidate
`c9d2f61f1f6d39c233907db88073e6c9737ca7ec` already owns pinned import,
schema-1 neutral expectations, full and filtered generation, offline checking,
provenance reports, and atomic publication. Its current CSS fixture decoder
accepts one ordinary object per non-`error` label and therefore cannot derive
the pinned grouped-array corpus.

Implementation of this initiative shall not begin until a reviewed, published,
and fetchable `surgeist-generator` candidate proves all of these consumer
requirements:

1. It imports the exact 74-file pinned tree without executing upstream code.
2. It derives exactly 935 cases, preserving all 721 parsed and 214 rejected
   outcomes.
3. It accepts object and array groups under every upstream label.
4. It classifies outcome per case object rather than by the enclosing label.
5. It assigns every grouped member a stable, unique, deterministic case ID.
6. It preserves case context, source, options, canonical CSS when present,
   disposition, and reason in canonical neutral expectations.
7. `check-corpus` validates the resulting committed import, expectations, and
   report without a source checkout or network access.
8. Generator-side focused tests cover mixed parsed/rejected arrays, duplicate
   identities, ordering, and canonical output.

The generator owns the exact stable grouped-case ID grammar. This initiative
treats each generated ID as an opaque validated identity and shall not reproduce
the generator's ID derivation.

### 3.4 Initiative Dependency

`P01/I01` must be implemented, reviewed, published, and closed before the first
implementation cycle for this initiative. The harness consumes the final
browser-compatible parse-report and `app-strict` validation behavior established
there. A contradiction or later material revision in that public contract
invalidates the affected harness planning and requires reconciliation before
implementation.

The generator prerequisite and `P01/I01` are entry gates, not hidden tasks in
this CSS-owned initiative. Their owning repositories and cycles retain their own
implementation, review, publication, and handoff responsibilities.

## 4 Corpus Artifact Contract

### 4.1 Repository Layout

The committed corpus root shall be
`tests/corpus/csstree/`. It shall contain:

```text
tests/corpus/csstree/
|-- LICENSE
|-- README.md
|-- corpus.toml
|-- source/
|   |-- .surgeist-source.json
|   `-- atrule, declaration, media, rule, selector, stylesheet, and value fixtures
`-- expectations/
    |-- generation-reports/
    |   `-- all.json
    `-- neutral expectations mirroring the 74 imported fixture paths
```

`source` and `expectations` are generator-owned trees. They shall be changed only
through the authoritative generator. `LICENSE` and `README.md` are CSS-owned
attribution and maintenance artifacts and shall remain outside generator-owned
trees.

The integration-test source and private support modules shall live under
`tests/` but outside `tests/corpus/csstree/`. The CSS-owned per-case oracle shall
live at `tests/csstree/oracle.json`, separate from generator-owned artifacts. No
generated Rust source belongs in the corpus.

### 4.2 Manifest And Provenance

`corpus.toml` shall use the generator's supported CSS manifest schema and pin:

- the canonical CSSTree HTTPS repository;
- source revision
  `88e3d965c0b1628642a30a841745b410d6835052`;
- fixture root `fixtures/ast`;
- expected file count `74`;
- expected case count `935`;
- distinct one-component import and expectation roots;
- the canonical full-report path;
- no generator disposition override.

The source sidecar shall bind the exact Git revision, file set, file modes, and
digests. The full generation report shall bind the manifest, source sidecar,
expectation files, case counts, dispositions, and output digests.

All neutral expectations shall retain generator disposition `Active`. The full
report shall therefore record 935 active, zero expected-fail, zero unsupported,
zero quarantined, and zero failed-to-generate cases. Those values describe
successful neutral derivation only. Surgeist-specific conformance and unsupported
classification belong exclusively to the CSS-owned oracle in 5.4.

The committed `README.md` shall record the upstream repository, revision, package
version, fixture tree object, license, compatible generator candidate, generation
boundary, ordinary test boundary, and update procedure. It shall not claim that
CSSTree itself runs as part of Surgeist verification.

### 4.3 License Preservation

The committed corpus `LICENSE` shall preserve the exact upstream MIT notice from
the pinned checkout. Any source-revision update shall compare upstream licensing
before publication. A changed license or attribution is a new review input and
blocks regeneration until the owning terms are reflected correctly.

### 4.4 Generated Artifact Integrity

Ordinary integration tests shall read only canonical expectation files named by
the generation report. They shall reject:

- a missing or additional reported artifact;
- a report count that differs from its case inventory;
- duplicate source paths or case IDs;
- an unknown schema version or generator identity;
- a case whose context disagrees with its fixture path;
- any neutral disposition other than active or any neutral reason;
- an unrecognized upstream outcome or context;
- an expectation file containing no cases;
- an oracle record that matches no case or a case with no oracle record.

The authoritative generator's `check-corpus` remains the complete digest and
provenance verifier. The Rust harness shall not duplicate Git source
verification, source-sidecar reconstruction, or publication-history logic.

## 5 Test Consumer Model

### 5.1 Phase Boundary

All corpus consumer types are private integration-test types. They model
persisted neutral expectations and adapted public-API probes; they do not become
production syntax, public API, or a generic CSS value model.

The consumer model shall separate these phases:

1. persisted expectation records deserialized from canonical JSON;
2. validated corpus records with unique identities and complete metadata;
3. adapted complete CSS source with a known payload span;
4. observed public parser and validator outcomes;
5. an oracle comparison that yields zero or more typed case mismatches.

No broad map or stringly typed bag may cross those phases.

### 5.2 Semantic Types

The private test model shall include semantic equivalents of:

- `CsstreeCaseId`, a non-empty opaque case identity;
- `CsstreeFixturePath`, a validated expectation-relative JSON path;
- `CsstreeContext`, a closed enum for the eleven pinned contexts;
- `CsstreeUpstreamOutcome`, exactly `Parsed` or `Rejected`;
- `NeutralCaseDisposition`, which accepts only the generated active state;
- `CsstreeCase`, the validated source, context, options, upstream outcome,
  neutral disposition, and optional canonical CSS;
- `CsstreeProbe`, a closed enum naming one complete-input adaptation;
- `AdaptedCssCase`, complete CSS source plus the exact byte span occupied by the
  upstream payload;
- `ExpectedSurgeistOutcome`, a closed enum distinguishing clean acceptance,
  diagnosed recovery, strict rejection, and recognized unsupported behavior;
- `CsstreeMismatch`, a closed enum containing case identity and structured
  expected/observed evidence.

Fields that participate in invariants shall remain private. Fallible
deserialization shall be followed by one validation boundary; test execution
shall accept only validated records.

### 5.3 Disposition Invariants

At initiative completion:

- every one of the 935 cases executes;
- CSS-oracle `ExpectedFail` count is zero;
- CSS-oracle `Quarantined` count is zero;
- every `Active` case has one executable probe and one exact expected Surgeist
  outcome;
- every `Unsupported` case still executes for panic-freedom and has a stable
  reason identifying an out-of-profile upstream construct, an option contract
  the public API intentionally does not expose, or a fragment that cannot
  truthfully test property-specific validity through a complete stylesheet;
- no unsupported reason may mean currently broken, not implemented yet, flaky,
  difficult, or unknown.

An active mismatch is a test failure. An unsupported case that begins satisfying
an active adapter policy is also a test failure requiring reviewed
reclassification, so coverage improvements cannot remain invisible.

### 5.4 CSS-Owned Per-Case Oracle

`tests/csstree/oracle.json` is the sole authority for adapting and judging the
neutral cases as Surgeist tests. It shall be canonical pretty JSON with one final
line feed and this top-level model:

```text
CsstreeOracleFile {
    schema_version: 1,
    source_repository,
    source_revision,
    source_tree,
    expectation_schema_version: 1,
    generation_report_sha256,
    cases: [CsstreeOracleCase; 935],
}
```

The notation describes fields and cardinality, not Rust public API. The file
shall contain exactly one record for every generated opaque case ID, sorted by
that ID. Each record shall contain:

- the exact case ID;
- the expected fixture path and context, used to detect accidental rebinding;
- one closed `CsstreeProbe` value, including any property, descriptor, at-rule,
  or wrapper identity required by that probe;
- exactly one closed `ExpectedSurgeistOutcome` value;
- an optional unsupported reason only when the expected outcome is
  `Unsupported`.

The expected-outcome choice is exactly:

- `Clean`, requiring a clean browser-compatible report and successful
  application-strict validation;
- `Recovered`, requiring a non-empty report diagnostic set, one non-empty
  oracle-authored set of required typed recovery actions, and
  application-strict rejection;
- `StrictRejected`, requiring a non-empty report diagnostic set, one
  oracle-authored typed rejection category, and application-strict rejection;
- `Unsupported`, requiring one execution policy and one reason class from 9.3;
- `ExpectedFail` and `Quarantined`, recognized by the loader solely so either
  value produces a pinned completion-count failure.

`Clean`, `Recovered`, and `StrictRejected` are the three active conformance
outcomes. `Unsupported` is executed non-conformance coverage. No separate active
boolean or disposition field may contradict the selected outcome.

An unsupported execution policy is exactly one of:

- `RecognizedUnsupported`, with the required public diagnostic category;
- `RecoveredUnsupported`, with a non-empty required recovery-action set;
- `PanicFreedomOnly`, with a balanced containment probe for a fragment that has
  no truthful conformance adapter.

The generation report digest binds the oracle to the exact neutral artifact set.
Any import, expectation, report, case-ID, context, source, option, or canonical
CSS delta changes that digest and makes the oracle stale until every affected
record is reviewed. There is no prefix, context, fixture-path, or default outcome
fallback: fixture-level adapter policy may help author records, but executable
tests consume only the explicit per-case records.

Corpus loading shall prove a bijection between generated case IDs and oracle
records before executing a parser call. It shall also prove that each record's
fixture path and context match the generated case, that its probe is legal for
that context, that the expected outcome is compatible with upstream outcome, and
that its unsupported reason or required typed diagnostic set satisfies the
selected variant's cardinality.

### 5.5 Options

Upstream options shall deserialize into a closed test-only options model. Each
observed option combination must be either consumed by its selected probe or
classified unsupported with a reason. Unknown keys, wrong value types, and new
combinations fail corpus loading.

The harness shall not interpret `parseValue: false`, `parseRulePrelude: false`,
or `parseAtrulePrelude: false` as ordinary CSS grammar. Those options alter
CSSTree AST construction and require explicit unsupported or recovery policy.

## 6 Context Adaptation

### 6.1 Complete-Input Rule

Every active probe shall produce one complete stylesheet or style-attribute
input accepted by the final public front door. The adapter shall preserve the
upstream source byte-for-byte inside the adapted input and record its exact
payload byte span.

Wrappers may add only fixed ASCII syntax with semantics selected by the probe.
They shall not repair, normalize, escape, reorder, or delete upstream bytes. A
wrapper must remain valid when its payload is valid and must localize a payload
failure rather than introduce an unrelated failure.

### 6.2 Probe Families

The closed probe inventory shall cover these roles:

| Context | Required adaptation policy |
| --- | --- |
| `stylesheet` | Parse the source directly as a sheet. |
| `rule` | Parse a complete rule directly when its fixture contract is top-level; otherwise use one explicitly named legal group-rule wrapper. |
| `atrule` | Parse directly only when the at-rule is legal at the selected level; use an explicit legal wrapper for context-restricted forms. |
| `declarationList` | Wrap as the declaration body of a fixed valid style rule. |
| `declaration` | Wrap as one declaration inside a fixed valid style rule. |
| `block` | Insert the block content at the exact block-owned location selected by a named probe. |
| `selectorList` | Use the payload as the complete selector list of a fixed valid style rule. |
| `selector` | Use a fixture-specific selector probe; fragments that cannot form a truthful complete selector are unsupported. |
| `mediaQuery` | Use the payload as one complete query or query list in a fixed `@media` rule. |
| `atrulePrelude` | Use the typed upstream `atrule` option to select a supported at-rule wrapper. |
| `value` | Use a fixture-specific property or descriptor whose grammar truthfully owns the tested token form; generic token preservation alone is not property validity. |

The adapter registry shall be exhaustive over all 74 fixture paths. A new or
renamed fixture has no default fallback and fails completeness validation.
Fixture policy is an authoring aid only; the committed per-case oracle remains
the executable source of each probe and expected outcome.

### 6.3 Property And Descriptor Probes

A value probe shall name its owning supported property or descriptor. Examples
include color syntax through `color`, sizing calculations through `width`,
strings through `content`, URLs through an image-valued property, and Unicode
ranges through the supported `@font-face` descriptor.

Using a custom property is valid only for cases whose oracle is balanced authored
token preservation. It shall not be used to claim that a dimension, color,
number, percentage, URL, function, or calculation is valid for an ordinary
property.

When no supported public property or descriptor truthfully owns a generic value
fragment, the case remains executed as unsupported. The initiative shall not add
a public generic-value parser solely to activate such a fixture.

### 6.4 Source Positions

For rejected and diagnosed-recovery cases, at least one public diagnostic span
shall intersect the adapted payload span or point at its end when the required
diagnostic is an end-of-input implicit closure. A diagnostic that points only
into fixed wrapper syntax is a harness or parser failure.

Exact upstream offsets and diagnostic prose are not imported and therefore are
not compared. Existing focused tests continue to own exact Surgeist diagnostic
categories, positions, spans, and recovery actions.

## 7 Oracle Contract

### 7.1 Browser-Compatible Parsing

Every case shall call the final public browser-compatible parser inside
`std::panic::catch_unwind`. An unwind is recorded as a case mismatch and shall
not prevent later corpus cases from executing.

For an active upstream-parsed case expecting clean acceptance:

- the public call returns its normal parse-report result;
- the report contains validated syntax;
- `is_clean()` is true;
- the diagnostic slice is empty.

For an active upstream-parsed case expecting diagnosed recovery:

- the report contains validated retained syntax;
- `is_clean()` is false;
- at least one typed recovery diagnostic is present;
- each checked action/category is asserted structurally rather than by display
  text;
- application-strict validation rejects the same adapted source.

For an active upstream-rejected case:

- browser-compatible parsing does not unwind;
- the report contains no invalid or unchecked syntax node;
- at least one typed recovery diagnostic accounts for the rejected payload;
- application-strict validation rejects the same adapted source.

### 7.2 Application-Strict Validation

With feature `app-strict`, every active clean case shall return its syntax value.
Every active diagnosed-recovery or upstream-rejected case shall return
`CssValidationFailure` with a non-empty diagnostic slice. The validation result
shall agree with the already observed browser-compatible report and shall not be
produced by a second test-only grammar.

The harness shall not depend on feature unification changing parser behavior.
Browser-compatible corpus tests run both without and with `app-strict`; their
observed syntax and diagnostics must remain identical.

### 7.3 Unsupported Cases

Unsupported cases execute the same panic-freedom boundary. Their expected
diagnostic or non-clean result shall be asserted when the public model can state
it truthfully. A case that has no truthful complete-input adapter may use a
minimal balanced containment probe solely to establish no unwind; that probe
must be named as non-conformance evidence and shall never count as active
acceptance or rejection coverage.

### 7.4 Canonical CSS

The consumer model shall preserve optional `canonical_css` so schema drift is
detected, but no test shall compare it to Surgeist output in this initiative.
Activating that field requires a separately designed authored-syntax serializer
owned by `surgeist-css`.

## 8 Test Execution And Reporting

### 8.1 Integration-Test Boundary

The corpus harness shall be a Rust integration test. It may import only the
public `surgeist_css` crate API. It shall not use path attributes, source-file
inclusion, feature tricks, or public test hooks to reach private implementation.

Private harness support may deserialize corpus artifacts, adapt sources, invoke
public functions, and compare outcomes. No helper introduced for the corpus may
be reexported from `src/lib.rs`.

### 8.2 In-Process Loading

One `OnceLock`-backed validated corpus shall be shared by every context-family
test in the integration-test binary. Loading shall:

1. read the committed full report;
2. resolve its sorted expectation inventory beneath the fixed corpus root;
3. deserialize each expectation;
4. hash and deserialize the CSS-owned per-case oracle;
5. validate schema, identities, counts, contexts, neutral dispositions,
   report-digest binding, the exact case/oracle bijection, and probe coverage;
6. expose immutable validated cases grouped by `CsstreeContext`.

The harness shall perform no subprocess launch, network access, checkout
inspection, source import, generation, arbitrary sleep, or polling.

### 8.3 Failure Aggregation

Each context-family test shall execute every case in that context, collect every
mismatch, sort mismatches by stable case ID, and fail once with the complete
structured mismatch list. A first failure shall not hide later cases in the same
family.

Failure output shall include:

- case ID and fixture path;
- context, upstream outcome, and CSS-oracle outcome;
- selected probe;
- expected Surgeist outcome;
- observed result or captured panic marker;
- diagnostic codes/actions relevant to the mismatch;
- the adapted source and payload span, with control characters escaped.

Tests shall match typed errors, diagnostics, actions, and dispositions. Display
strings are diagnostic output only.

### 8.4 Speed

The complete corpus remains an ordinary non-ignored test surface. It shall not
be marked slow, browser, network, external, or nightly. The implementation shall
record observed wall-clock evidence for the focused corpus test in the cycle
handoff, but shall not add a flaky elapsed-time assertion.

Any future change that introduces per-case process startup, browser work,
generator execution, network access, or repeated whole-corpus deserialization is
a regression in this contract.

## 9 Coverage And Classification

### 9.1 Completeness Ledger

The harness shall compute and assert:

- 74 expectation artifacts;
- 935 unique case IDs;
- 721 upstream-parsed cases;
- 214 upstream-rejected cases;
- the exact eleven-context totals in 3.1;
- zero expected-fail cases;
- zero quarantined cases;
- active plus unsupported equals 935;
- every fixture path has exactly one adapter policy;
- the CSS-owned oracle and generated cases form an exact 935-entry bijection;
- the oracle's generation-report digest matches the committed report bytes.

These values are pinned-revision facts. Updating them requires a reviewed source
revision change and regenerated artifacts.

### 9.2 Active Coverage

An active case is a conformance assertion, not merely a smoke test. It must have
a truthful public-API probe and exact expected clean, recovered, or strict
rejection behavior.

The active inventory shall include every pinned case whose grammar lies in the
completed `P01/I01` profile and can be represented through a public complete
stylesheet or style-attribute entry point. A claimed-complete grammar case may
not be made unsupported because the current implementation fails it.

### 9.3 Unsupported Coverage

Unsupported reasons shall use a finite private enum and render stable reason
text into the CSS-owned per-case oracle. The completion inventory may use only
these reason classes:

- outside the selected CSS profile;
- vendor-specific or host-specific syntax not claimed by the crate;
- upstream parser-construction option with no equivalent public CSS grammar;
- generic fragment lacking a truthful supported property or descriptor probe;
- AST-construction behavior with no acceptance/rejection meaning at the
  stylesheet public boundary.

Each unsupported case still contributes panic-freedom evidence. Any new reason
class is a material specification change.

### 9.4 Relationship To Focused Tests

The corpus proves broad independent parser behavior. Focused crate tests remain
the authority for:

- exact authored syntax structure and private-constructor invariants;
- exact property-specific and descriptor-specific value models;
- exact recovery action, diagnostic code, source position, and span;
- support-catalog completeness and specification-tier mapping;
- nesting limits and targeted adversarial inputs;
- public API shape and compile-time feature behavior.

A corpus pass cannot excuse a failure in those tests, and a focused test pass
cannot excuse an active corpus mismatch.

## 10 Dependencies, Features, And Compatibility

### 10.1 Cargo Dependencies

Production dependencies remain unchanged. The harness may add only these
test-only dependencies, pinned compatibly with the generator's persisted JSON
contract:

- `serde` with derive support;
- `serde_json`.

No JavaScript, browser, async-runtime, generator, Git, HTTP, archive, directory
embedding, snapshot-testing, or test-runner dependency is permitted.

If the exact pinned crates are not already available when implementation begins,
dependency acquisition requires the then-applicable explicit authorization and
license/advisory review. The implementation cycle records the exact versions,
licenses, MSRV compatibility, and lock behavior.

### 10.2 Features

The corpus integration test shall compile and run in:

- the default browser-compatible feature set;
- `--features app-strict`.

The default build must not compile a strict-only call site. Strict assertions
shall be feature-gated in the integration test without changing the default
browser-compatible oracle.

### 10.3 Public API And SemVer

The initiative adds no production public API and is SemVer internal-only.
Corpus files, test support, dev dependencies, and documentation are not a
promise that downstream crates can import the harness.

If implementation evidence shows that a new production front door is necessary,
the cycle stops and the specification is materially revised and re-reviewed.
The test initiative may not smuggle such an API through as a convenience.

### 10.4 MSRV And Unsafe

The harness shall preserve the crate and root integration MSRV current when its
cycle begins. Every repository-authored Rust test file remains
`#![forbid(unsafe_code)]` compatible and contains no unsafe construct or
unsafe-enabling allowance.

## 11 Corpus Maintenance

### 11.1 Initial Import

The initial corpus publication shall use the reviewed compatible
`surgeist-generator` candidate and the already downloaded explicit checkout at
`tmp/csstree`. It shall run import, full generation, and offline check through
the generator's public CSS binary contract. It shall not invoke any upstream
package script.

Generated source, sidecar, expectations, and report shall be reviewed as one
artifact set with `corpus.toml`, upstream `LICENSE`, attribution `README.md`,
CSS-owned per-case oracle, adapter registry, and harness.

### 11.2 Ordinary Verification

Ordinary Cargo tests use only committed artifacts. A missing `tmp/csstree`
checkout, missing Node.js installation, offline host, or absent browser shall
not change compilation or results.

The generator's offline `check-corpus` is an explicit artifact-maintenance and
cycle-final command. It is not called recursively from `cargo test`.

### 11.3 Source Updates

A future CSSTree update is an explicit reviewed corpus migration. It shall:

1. record the proposed repository revision and license;
2. inventory file, case, context, option, grouped-array, and outcome changes;
3. update the exact manifest pin and counts;
4. regenerate through the authoritative generator;
5. reconcile every new, removed, or changed per-case oracle record and adapter;
6. run the complete public-API harness and focused crate checks;
7. explain every active/unsupported movement and generated delta.

No automation shall track upstream `master`, npm releases, tags, or moving
references.

## 12 Implementation Outline

### 12.1 Corpus Consumer Modules

The integration-test implementation shall keep responsibilities separate:

- persisted JSON records and deserialization;
